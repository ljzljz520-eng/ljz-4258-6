# 离线记事实与在线授权边界

## 1. 离线时可以成立的“事实”

- 操作员在现场看到的温度、pH 值：保存到 IndexedDB，恢复网络后通过 `/sync` 上传。
- 设备来源序号由采集端按 `source_id` 单调递增；后端以 `(batch_id, source_id, source_seq)` 去重。
- 原始 `collected_at` 是设备/操作员声明的采集时间，永久保留，不会被补录时间或接种签发时间覆盖。
- 时钟漂移以 `calibration_anchors` 记录锚点，并派生 `corrected_collected_at = collected_at + clock_offset_ms`。原始字段和校准字段同时保存。
- 离线期间点击接种按钮，只保存为 `offline_inoculation_attempt` 且 `accepted=false` 的操作事实，用于审计“有人尝试过”，不产生签字资格。

## 2. 必须在线由后端授权的事项

- 接种双签的每一次有效签名。
- 菌种、奶基、接种、冷却、灌装状态机推进。
- 菌种换绑/换签及批次版本递增。
- 冲突批次进入或退出 `reconcile_required`。
- 接种签发：后端重新检查证据、时钟锚点、来源水位、当前菌种状态、奶基状态以及两名签字人的实时资格。

## 3. 为什么离线两次点击不能双签

有效签名写入 `inoculation_confirmations`，该表对 `(batch_id, batch_version, culture_version_id, signer_id)` 建唯一约束。请求必须携带当前登录用户的有效 Bearer 会话；后端不信任客户端提交的“我是另一个人”。因此：

- 同一账号连续点两次：第二次得到 `SAME_ACCOUNT`。
- 两个离线队列事件：同步时只记录未授权尝试，得到 `OFFLINE_CANNOT_ISSUE`。
- Alice 先签后换菌种版本：版本递增，旧 `(batch_version,culture_version_id)` 签名不参与新双签。
- 签字时合格、签发前被取消资格：第二签触发后端复查，进入阻断和待协调。

## 4. 证据水位

每个罐有温度和 pH 两个来源。后端维护每来源连续水位：从序号 1 开始，无缺口才递增。接种签发要求：

1. 两类来源均存在；
2. 两类来源至少有连续序号 1；
3. 两类来源均有校准锚点；
4. 没有开放的来源序号冲突/缺口协调项；
5. 两名签字人不同、实时具备 `can_inoculate=true`；
6. 两人绑定的是同一个当前 `batch_version` 与 `culture_version_id`。

晚到数据不重写历史。例如先收到 `#1、#3` 会对 `#2` 开立缺口；之后 `#2` 到达，标记为 `out_of_order=true`，缺口自动关闭，图表仍按来源序号排序。

## 5. 软件边界

系统只记录、校验和展示，不：

- 推荐接种量、菌种比例或工艺参数；
- 自动启停冷却；
- 将 pH/温度阈值解释成工艺控制指令；
- 用后补的接种时间改写设备或人工记录的原始采集时间。

范围校验仅用于识别明显录入错误（例如 pH 不在 3–8），不是工艺建议。
